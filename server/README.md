# URBAN KASHI backend handoff

Node **24+** is required for `node:sqlite`. Catalogue CSV parsing requires `csv-parse`. Database amounts are **integer INR rupees**; gateway requests use exact trusted totals × 100 in INR paise. COD is always available; optional Razorpay Checkout requires all three protected gateway values. No payment-provider success is simulated. See [payments and catalogue operations](../docs/PAYMENTS_AND_CATALOGUE.md) for the authoritative new contracts, pending-review/refund workflow and import template.

This is an independently owned website with its own accounts/database/inventory. **No POS synchronization ever**; no POS APIs, credentials or shared data and no edits to the adjacent POS project. Existing POS barcode text may be manually mapped into owner-supplied CSV. No actual POS export file has been supplied or verified.

## Configuration and administrator creation

The server and admin CLI load private root environment configuration through `dotenv`; [.env.example](../.env.example) supplies safe defaults. `DATABASE_PATH` is relative to the working directory; `PORT` defaults to `8080`, `HOST` to `127.0.0.1`. `COOKIE_SECURE=true` enables secure cookies and HTTPS security headers; keep it false for local HTTP. Set true behind production HTTPS. Keep the database, backups, environment files and credentials outside the compiled static root and other publicly served paths. Startup refuses a database inside its static root.

`UPLOADS_PATH` configures the private photo directory. Blank is valid: [server/index.ts](../server/index.ts) passes `process.env.UPLOADS_PATH || undefined`, selecting a `product-images` directory beside the database (normally **data/product-images**). Relative overrides resolve from the working directory. Upload and compiled public directories must not overlap, and the database must not sit inside the upload directory. The fixed default managed-image quota is **200 MiB**; only trusted `AppOptions.uploadsQuotaBytes` can override it. There is **no quota environment variable**. Persist and back up both the database and photo directory.

Optional online payments require `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET` in the protected **server-only** environment. Missing/incomplete configuration or an invalid key-ID format disables online checkout; it does not verify credentials or merchant eligibility. Only the public key ID is exposed to Checkout. Never use `VITE_` secrets or send credentials in chat. Start with owner-controlled test keys, configure a **public HTTPS signed webhook** at the exact `POST /api/payments/webhook`, subscribe to `payment.captured`, `order.paid`, `payment.failed` and `refund.processed`, and enable provider-side capture. Authorized payments remain pending; no capture request is issued by this backend. All UPI/Card/Netbanking/Wallet/EMI/Pay Later availability is conditional on merchant KYC/activation, transaction/customer eligibility and provider support. Follow the [sandbox setup and official references](../docs/PAYMENTS_AND_CATALOGUE.md) before any live activation.

For noninteractive administrator creation, supply **all three** `ADMIN_EMAIL`, `ADMIN_NAME`, and `ADMIN_PASSWORD` through a protected process environment, then invoke the existing `admin:create` script. Never put the password in command-line arguments, source control, chat, a shared terminal transcript or committed environment files. Clear it from the calling environment afterward. The CLI does not log passwords, hashes, or tokens. Existing accounts are **not** silently promoted or overwritten. Password policy: 10–72 UTF-8 bytes with at least one letter and one digit. Bcrypt cost is 12.

Admin access requires the server-side `admin` role; an authenticated customer remains restricted. The creation CLI rejects an existing email and does not promote existing customers. The current owner's role was not verified during the static review. If a separately authorized operator has already granted the role and revoked old sessions, sign out and sign back in with that account's existing password in an approved environment. Reauthentication does not itself grant a role. If still restricted, an authorized operator must verify the account and intended website database; never reset the database or bypass authentication to obtain access. Promotion is not a public API; omit all real account identifiers and credentials from source/docs.

## Behavior and assumptions

- API response shapes match [shared/types.ts](../shared/types.ts); failures are `{ error: string }`. Authentication uses seven-day, HttpOnly, SameSite=Lax, opaque cookie sessions; only SHA-256 token hashes are stored. Login rotates the browser's previous session. No credentials or session tokens appear in JSON. Logout revokes the session server-side.
- Every mutating `/api` browser request needs `X-Requested-With: UrbanKashi`; cross-site Fetch Metadata writes are rejected. The only header exception is the exact signed raw POST payment webhook. No permissive CORS is enabled. API caching is disabled. Normal JSON request bodies are limited to 32 KiB; the two admin CSV endpoints allow a 2 MiB JSON body, the webhook allows a 2 MiB uncompressed raw body, and the exact image-upload endpoint accepts up to 10 MiB of binary image data, not JSON/multipart. Login/register share a 20-per-15-minute IP limit, with a separate 300-per-minute general API limit.
- Proxy headers are **not trusted**. Behind a reverse proxy, configure a precise trusted proxy policy before changing this; by default requests behind that proxy share its IP limit. Multi-process deployments need a shared external rate-limit store; the current limiter is appropriate for a single-process local service.
- Checkout requires 1–20 lines, integer quantities 1–10, safe nonempty size text up to 24 characters, and an 8–128-character alphanumeric/hyphen/underscore idempotency key. Products accept up to 30 sizes. Duplicate product/size lines are rejected, not merged. Addresses require an Indian mobile number (optional `+91`) and six-digit nonzero-leading pincode; they are format-validated, not delivery-verified.
- Client prices/totals/payment overrides and other unknown body fields are rejected. The server recomputes all prices, adds ₹99 shipping below ₹2499, and snapshots the address and line items in one `BEGIN IMMEDIATE` stock/order transaction. Stock decrements are conditional; any failure rolls back all lines.
- Idempotency is scoped to the signed-in user. Canonically sorted validated items/address are hashed. Matching retries return the existing order with HTTP 201, even after cancellation; mismatched reuse returns 409. A retry never reserves stock twice.
- Order lists are owner-only; admins can inspect any order. Admin transitions: placed → confirmed/cancelled; confirmed → shipped/cancelled; shipped → delivered. Online confirmation/shipment requires verified paid status **and no `paymentReview`**. Already-shipped orders may still be recorded as delivered despite a later payment/refund issue; this does not resolve that issue. Terminal and same-status updates return 409. Cancellation restores stock exactly once in the same transaction, recreating a removed variant with snapshot identifiers when safe. Conflicting reused identifiers fail atomically with 409. Paid cancellations/late captures require a manual provider refund, not automatic fulfilment or an automatic refund call.
- Admin variant arrays replace current absolute stock counts atomically, rather than expressing deltas. CSV upserts preserve omitted variants/products. There is no product-delete endpoint. Product edits do not alter historical order snapshots. Admin stats count all catalogue products/orders, customer-role accounts, and noncancelled COD or verified paid online totals **including shipping**. Online revenue requires `payment_status = 'paid'` **and `payment_review IS NULL`**; pending, refund-required, refunded and held online orders are excluded. COD revenue is booked order value, **not verified collected cash**.
- Images accept HTTPS URLs or restricted same-site paths. The CSP permits self-hosted scripts/fonts/connections, inline CSS, and HTTPS product images. When a gateway is configured it additionally permits Razorpay checkout scripts, frames and API connections on explicit provider hosts. Inline scripts and external Google Fonts remain disabled. Validate hosted Checkout in the owner's sandbox before launch. Unknown API paths never receive the SPA; only GET navigations explicitly accepting HTML receive its fallback.

## Direct photo uploads and inventory lifecycle

- `POST /api/admin/uploads/images` requires an authenticated admin, same-origin write checks and `X-Requested-With: UrbanKashi`. Send one raw binary file with exact `Content-Type: image/jpeg`, `image/png` or `image/webp`; no multipart or base64. Maximum **10 MiB**, **40 million pixels**, non-animated only. Authentication and concurrency admission occur before buffering. The default per-admin limit is **30 uploads/minute**, with **two concurrent processing slots**; excess concurrency returns 503 rather than queuing image bodies.
- The server validates framing and decoded format, applies orientation, converts to sRGB and writes **WebP quality 82**, fitting within **1600 × 1600 without upscaling**. Originals are not retained. Success is **201** `{path,bytes,width,height}`, where `path` is `/uploads/products/<uuid>.webp`. Files consume real disk and count against the **200 MiB** default managed quota, including matching crash leftovers; quota/disk exhaustion returns 507. Product image content is not stored in SQLite: products store paths and `image_uploads` stores registry metadata.
- Guarded GET/HEAD serving allows only registered UUID WebP regular files, not arbitrary directory access. The admin main/gallery controls send files **sequentially**, preview only confirmed results and retain earlier completed uploads if a later one fails. Up to 12 gallery paths are allowed. Save the product to attach paths; cancelling does not save the draft. Existing HTTPS URLs/safe paths remain supported.
- Managed uploads become cleanup candidates only when older than **24 hours** and unreferenced. The first observation marks them; a second check **at least 60 seconds later**, under the same SQLite write lock as deletion, checks every product main/gallery reference (including hidden/archived products) and historical order image. Referenced images remain. Archiving never removes photos; removing a product path does not delete a still-referenced file.
- When all sizes reach zero, stock mutations record `sold_out_at` transactionally. Active listings show **Sold out on the image for 48 hours**, then become inactive with `archived_at` set. This is a **soft archive**: storefront lists/detail lookup hide the product, admin retains it, and variants/barcodes/orders/snapshots/images are preserved. Positive restock before the deadline clears the timer. After archive, positive stock alone cannot republish: explicitly submit `active: true` with at least one stocked size (select **Active** in admin; CSV uses explicit `active=true`). Cancellation-restored stock alone does not republish.
- A **60-second** maintenance interval performs lifecycle and cleanup sweeps. Lifecycle is also enforced at request time and on startup, catching up persisted sold-out deadlines after downtime. Legacy all-zero products without a timestamp receive one on their first lifecycle check. This maintenance does not expire payment reservations or reconcile payments.

## Demo data and operations

The **12 seeded products, stock, product details, and Unsplash photographs are placeholders**, not verified sale inventory or actual product photography. Some images are reused. Seed photographs are cached as local public assets; administrators may also specify HTTPS URLs. The seed is recorded once in SQLite and does not replenish inventory on restart. `openDatabase(..., { seed: false })` and `createApp({ seed: false })` support empty test/integration catalogues. Replace or deactivate all demo products before a real launch.

Schema migrations **0 → 1 → 2 → 3** use SQLite `user_version`, foreign keys, WAL, strict tables, indexes, and a five-second busy timeout. V2 preserves v1 orders/snapshots/idempotency while rebuilding the COD-only and fixed-size CHECK constraints. V3 adds `sold_out_at`, `archived_at`, the lifecycle index and `image_uploads` without discarding existing accounts/sessions, catalogue identifiers, stock or order history. Newer schemas fail closed. Back up before migration; never replace the database to upgrade. Keep SQLite and photos on local persistent storage, not ephemeral deployment storage; SQLite must not use a network share. Entry points apply restrictive file-creation permissions where the OS supports them; enforce Windows ACLs separately. Back up **both the database and private photo directory** as a coordinated recoverable set, using a SQLite-aware procedure including committed WAL state; don't copy only a live main database file. Persist both across deployments and test restoring both together. Deployment still needs HTTPS, protected backups, log monitoring, real inventory review, and operational privacy/retention policies. No email verification, password recovery, automatic refund, capture-request automation, POS synchronization or automatic address verification is claimed. Online payments are confirmed only after server-side verification of provider capture.

The suite contains session-based coverage for registration, password policy, login/logout/expiry, authorization, headers, totals and tampering, idempotency, stock persistence, duplicate/invalid carts, address validation, transactional rollback, overselling, ownership, cancellation, admin product validation, status transitions, rate limits, and static-file isolation.

## Payment holds, refunds and stuck reservations

- A durable provider-creation claim prevents blind duplicate order submission after timeouts or crashes. Stock remains reserved for unknown outcomes. Support must review the local UUID receipt in Razorpay, reconcile a known provider order or recover an unbound outcome through a validated signed webhook. Do not ask the customer to pay again.
- The order page offers **Check payment status**, not a resume-payment button. There is no automatic reservation expiry or reconciliation scheduler. After authoritative provider review an admin can cancel a pre-shipment order to release stock once; local cancellation does not invalidate provider Checkout. Late capture does not revive cancellation and requires refund handling.
- Partial, ambiguous, inconsistent or incomplete refund evidence sets `paymentReview` and blocks confirmation/shipment and online revenue. This includes failed refund reads and incomplete pagination. Previously stored paid status may remain, but is not actionable while held.
- Full refund confirmation requires an exhausted, validated collection of unique INR refunds. Sum only **processed** refunds (multiple partial refunds can aggregate fully); failed refunds do not contribute and pending/unknown statuses cause review. The sum, payment `amount_refunded` and trusted order total in paise must agree, with payment status `refunded` and refund status `full`. For a refund event the fetched event refund must match the collection.
- Uncaptured refunded authorizations can be confirmed fully refunded **without inventing `paid_at`**. Existing timestamps are preserved. Stale capture reads cannot undo verified refunds or clear refund holds; conflicting payment identities require manual review and cannot be resolved by one payment's refund.
- Refund initiation is manual in the provider Dashboard; this backend only reads refund evidence. Payment/refund confirmation never changes inventory, automatically cancels/restocks fulfilled orders or restores cancelled fulfilment. There is no general admin force-clear-review endpoint.

## CSV and branding handoff

Use the [public/catalogue-template.csv](../public/catalogue-template.csv) template: one row per size, one slug per design + colour. In Excel set barcode/SKU to **Text before entering/importing values**, preserve leading zeros, then save **CSV UTF-8**. Admin accepts **CSV only, not XLSX**, with preview, explicit approval and final transactional revalidation. Maximum **1,000 data rows** and **2 MiB for the entire JSON body**, including escaping overhead. Stock is absolute website-allocated sellable stock; account for reservations before reimporting. Server limits: barcode ≤128 characters and SKU ≤160.

The website bundles Noto Serif Devanagari locally for the bilingual logo. Its crisp trishul is a new vector interpretation, not a genuine recovered original; upright `rotateY` animation respects reduced-motion. Downloadable [public/brand-logo.svg](../public/brand-logo.svg) is static, with font-dependent text rather than outlines or embedded fonts.
