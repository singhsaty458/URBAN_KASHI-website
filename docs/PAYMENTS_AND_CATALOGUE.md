# Payments and website catalogue

This independently owned website remains **disconnected from POS, with no synchronization ever**. No POS APIs, credentials, databases or runtime dependencies are used; never modify the adjacent POS project. Existing POS barcodes can be copied from an owner-supplied export into the website CSV as opaque text identifiers. **No actual POS export file has been supplied**, and real-export compatibility has not been verified. All template products, identifiers, stock and photographs are **dummy placeholders**, not verified inventory.

## Razorpay activation

The owner must create and verify an Indian Razorpay merchant account, configure payment capture, complete required compliance and enable eligible methods in the provider Dashboard. Provide **all three** values through the protected server environment:

- `RAZORPAY_KEY_ID`: the public checkout key (`rzp_test_…` or `rzp_live_…`).
- `RAZORPAY_KEY_SECRET`: private API/signature secret.
- `RAZORPAY_WEBHOOK_SECRET`: private webhook signing secret configured on the same provider endpoint.

Missing/incomplete/invalid key-ID configuration disables online checkout; COD remains available. Empty placeholders are supplied in [.env.example](../.env.example). Keep all configuration server-side; never prefix these values with `VITE_`. Do not commit secrets, send them to clients, put them in URLs, or paste them in chat/support transcripts. Only the public key ID is exposed. Test/live mode comes from the key ID; test transactions are not live collections. There is no fake payment success or client-selectable provider. Service tests inject an in-memory gateway or `paymentGateway: null`; adapter tests exercise `RazorpayGateway` with intercepted/mock HTTP and synthetic responses. Neither is external provider verification.

Standard Razorpay Checkout can offer **UPI, Cards, Netbanking, Wallets, EMI, Pay Later**, subject to merchant activation, currency, transaction, issuer/customer eligibility and provider availability. The methods list is not a promise that every option appears for every customer. This server does not automatically enable restricted methods or initiate a capture request; configure automatic capture with Razorpay and verify it before launch. Authorized payments remain pending until captured remotely.

### Owner-controlled sandbox setup — not yet externally tested

1. Create the merchant account, complete applicable KYC/compliance and review eligibility for each desired payment mode. A configured key or advertised method list does not prove live approval.
2. In Razorpay **Test Mode**, generate test API keys and enter the key ID/API secret through a protected server environment. Configure a separate webhook signing secret there and in the matching provider webhook. Never send any secret in chat. Restart the website after configuration changes.
3. Expose **only this website** through a public HTTPS deployment or trusted development tunnel; localhost alone cannot receive provider webhooks. Register the exact `https://<website-host>/api/payments/webhook` endpoint in the matching Test Mode Dashboard, with the signed events listed below. Do not expose or connect the POS. Use secure cookies with HTTPS.
4. Enable payment capture in the provider Dashboard. This application does not call a capture endpoint; authorization alone stays pending. Confirm current capture settings and method eligibility using the provider documentation.
5. Before live activation, exercise hosted Checkout/CSP, capture, signed webhook delivery/retries, lost callbacks, cancellation/late capture and partial/full refunds in the owner's sandbox. Verify order status, review holds, revenue exclusions and stock behavior. Use provider-documented test instruments, not real payment details.
6. Move to live keys only after merchant approval and successful external validation; configure the corresponding live webhook/secret and capture settings separately. Never treat a passing local test or test-mode payment as collected live revenue.

**No live or sandbox payment, external signed webhook delivery or real refund has been tested in this workspace.** These steps are activation instructions, not completed validation.

Official references: [Standard Checkout integration](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/), [API keys](https://razorpay.com/docs/payments/dashboard/account-settings/api-keys/), [webhook validation](https://razorpay.com/docs/webhooks/validate-test/), [payment capture settings](https://razorpay.com/docs/payments/payments/capture-settings/), [payment entity](https://razorpay.com/docs/api/payments/entity/), [refund entity](https://razorpay.com/docs/api/refunds/entity/), and [payment refund pagination](https://razorpay.com/docs/api/refunds/fetch-multiple-refund-payment/).

API requests use `https://api.razorpay.com/v1` with Basic authentication over verified HTTPS, no redirects, a 10-second `AbortSignal` timeout and sanitized errors. No provider exception bodies or credentials are logged. INR database amounts are integer **rupees**; gateway order/payment amounts must equal the trusted order total **times 100 in paise**, exactly. Individual refunds may be partial; only a fully validated aggregate equal to that original total can settle the order as refunded. Neither underpayment nor overpayment is accepted as a paid order.

### Frontend contracts

- `GET /api/payments/config` → `{online,keyId,mode,reason,methods}`; mode is `test`, `live` or `disabled`.
- `POST /api/payments/create` with `{items,address,idempotencyKey}` → **201** `{order,checkout}`. Checkout, when available, is `{key,order_id,amount,currency:'INR',name:'URBAN KASHI'}`. It is **null** when the order is cancelled, already settled, creating, or pending review. Preserve the same idempotency key for retries. Never substitute a new key following an uncertain outcome.
- `POST /api/payments/verify` with `{orderId,razorpay_order_id,razorpay_payment_id,razorpay_signature}` → `{order}`. Owner-only, including when caller is an admin: an admin must use reconciliation to inspect another user's payment. The HMAC uses the **stored** gateway order ID, then the server fetches the payment **and** provider order and checks ID, exact amount, currency, receipt and local-order notes. Paid requires `captured === true`, `status === 'captured'`, clean complete refund evidence and no unresolved hold. A valid signature alone is insufficient.
- `POST /api/payments/reconcile/:orderId` → `{order}`; owner or admin. Fetches provider order, payments and relevant refund collections. Use after modal close, lost callback, network interruption or delayed capture; it can also recover a missed refund notification. Modal dismissal does **not** imply payment failure, successful payment or stock release.
- Orders add public `paymentStatus`, `gatewayOrderId`, `paidAt`, and supplemental `paymentReview` (string or null). Internal payment IDs, provider creation state, payload hashes and idempotency keys are not exposed.

These payment browser writes require authentication, JSON and `X-Requested-With: UrbanKashi`; cross-site writes are rejected. Clients cannot set payment method/provider, amount, status or internal provider bindings. The separate admin photo endpoint uses raw image bytes instead of JSON and still requires admin authentication and the write-security header.

### Durable reservations, retries and pending review

1. Prices, stock decrement and local pending Razorpay order are persisted together in a synchronous SQLite transaction before any external request.
2. A durable compare-and-set moves the provider creation state from new to creating. Exactly one request may submit a provider order, even across concurrent app instances. Concurrent replays receive the same local order, possibly with null checkout while creation is in flight.
3. The provider receipt and `notes.local_order_id` are the local UUID. Its response is validated before the gateway order ID is bound durably.
4. Any ambiguous network, timeout, malformed response or process crash leaves the reservation intact and visibly unconfirmed. **No automatic retry of provider order creation** is attempted, even on an HTTP error. A crashed creating state is also a review state, not a retry opportunity.
5. A known provider ID can be reconciled. For an unknown provider ID, support must search the local UUID receipt in Razorpay Dashboard, establish whether an order/payment exists, and resend a relevant signed webhook. The server fetches and validates the provider receipt/notes before recovering a previously unbound creating/review order. There is no unauthenticated or arbitrary manual bind endpoint.
6. Admin order lists expose every pending reservation and `paymentReview`. Review these regularly; there is no background expiry job or silent indefinite stock release. After authoritative operational review, an admin may cancel locally to release stock, once, atomically. Local cancellation does not invalidate a still-open provider checkout; any later captured payment is handled as refund required. Do not cancel merely because a modal closed or a request timed out.

The order page provides **Check payment status**, but **no resume-payment button** to reopen hosted Checkout. Do not start a fresh checkout or use a new idempotency key to work around a stuck pending order. The order history, review notices, reconciliation action and admin pre-shipment cancellation are the current operational surfaces. Unknown outcomes require manual provider review; stock stays safely reserved until a reviewed cancellation releases it. There is no automatic refund, reservation expiry, reconciliation scheduler or provider-order cancellation. If the gateway is disabled during an incident, pending orders still remain visible; restore protected configuration to reconcile.

### Webhooks and refunds

Configure the public HTTPS endpoint **`POST /api/payments/webhook`**, and subscribe to `payment.captured`, `order.paid`, `payment.failed`, and `refund.processed`. Only this exact case-sensitive path and POST method bypass the XHR check; trailing slashes and alternative paths do not. The raw JSON **Buffer is read before any JSON parser**, maximum 2 MiB. `X-Razorpay-Signature` is verified with timing-safe HMAC-SHA256 against the exact bytes before JSON parsing. JSON reserialization changes the signature. `X-Razorpay-Event-Id`, or a raw-body digest fallback, is persisted after successful processing. Duplicate events and captures never decrement or restore inventory twice.

Notification text alone is not enough: relevant provider order/payment/refund entities are fetched remotely and validated against current state, not the event name's historical implication. Unconfirmed capture or failed order/payment reads return an error for provider retry/support resend. A refund-collection failure instead persists a review hold and can acknowledge the event safely; reconciliation is then needed. Failures/authorized attempts cannot downgrade a verified refund or clear an existing hold. Provider order/payment IDs have durable unique constraints. Multiple captured/refund-bearing candidates or conflicting payment identities persist a manual identity-review hold; one payment's refund cannot resolve a known identity conflict. Mismatched IDs/amounts are rejected rather than silently accepted.

**Confirming or shipping an online order requires `paymentStatus === 'paid'` and `paymentReview === null`.** A paid status with a review message is not permission to fulfil. Partial/ambiguous refunds and incomplete evidence block those transitions and exclude the order from online revenue, even if its stored status still says paid. **An already-shipped order may still transition to delivered** to record physical delivery; this does not clear a payment/refund issue. Admin cancellation of a paid order sets `refund_required`. A later clean verified capture after cancellation also sets `refund_required` and keeps the order cancelled. Stock is not reserved again.

Refunds are **initiated manually via the Razorpay Dashboard** until a separate audited refund workflow exists. Cancellation never calls a refund-creation API; the adapter's refund endpoints are read-only. Verification, reconciliation and signed webhooks use the same refund evidence rules:

- Fetch the relevant payment's complete refund collection, validating unique refund IDs, matching payment IDs, INR currency, positive integer paise amounts and terminal statuses. For `refund.processed`, the separately fetched event refund must also match an item in the collection exactly.
- The adapter requests pages of 100 using `count`/`skip`. Response `count` is the page size, not the grand total. A short/empty final page proves exhaustion; matching money totals alone do not. Duplicate/repeated pages, inconsistent counts, wrong-payment entries, failed reads or an unexhausted ten-page bound leave evidence incomplete and on hold.
- Sum **processed** refund amounts; failed refunds do not contribute. Pending/unknown statuses, partial totals, conflicting fields, missing evidence or over-refunding cause `paymentReview`, not a fully refunded result. Several individually partial **processed refunds may aggregate to a full refund**.
- Mark `refunded` only when the collection is complete and its processed sum equals the trusted original total, and the payment simultaneously reports `status === 'refunded'`, `refund_status === 'full'` and `amount_refunded` equal to that same total. A terminal provider flag by itself is insufficient.
- A fully verified **uncaptured refunded authorization** (`captured === false`) is valid: it must not invent `paid_at` / `paidAt`. Existing capture timestamps are preserved; captured payments may record a timestamp if previously absent.
- A stale clean capture or ordinary failed/authorized attempt cannot clear a bound refund hold. Only a fully verified refund clears that refund hold automatically; known conflicting payment identities remain a manual provider-review case. The separate initial unbound creation hold can resolve through a validated provider binding/capture.
- Once fully refunded, stale/reordered capture reads cannot change the status back or invent a later capture timestamp. Capture/refund confirmation never changes stock, revives cancellation or automatically cancels/restocks a fulfilled order.

Review holds need authoritative provider investigation, not a direct database edit to force paid status. There is no general admin “clear payment review” endpoint. Admin revenue includes noncancelled COD booked totals and online paid totals **only without a review hold**; it excludes pending, refund-required, refunded and held online orders. COD booked value is not proof that cash was collected.

## Catalogue model and migration

Use **one product slug per design + colour**, with one variant per size. White and navy editions of the same design must be separate slugs. Product metadata includes brand/design (legacy default empty strings), colour, description, photos, category and prices. Variant fields are size, stock, barcode and SKU. Cart selection remains `productId + size`; the product determines colour. Order snapshots retain name, image, price, brand, design, colour, barcode and SKU and never change after catalogue edits.

Sizes are safe nonempty text up to **24 characters**, e.g. XS, XXL, 3XL, 30, 32, Free Size; a product accepts up to **30 variants**. Letters/digits (including Unicode) followed by letters/digits/spaces/dot/underscore/slash/hyphen are allowed. Cart limits remain 20 lines and quantity 10 per line. Prepare **barcodes up to 128 characters and SKUs up to 160 characters**, without control characters. Both are TEXT: leading zeroes and case survive, while surrounding whitespace is trimmed. Nonempty barcodes are **globally unique with case-sensitive comparison**; SKU is not globally unique. Legacy/regular API products may have blank barcodes.

The server enforces the separate 128-character barcode and 160-character SKU limits. Exact-distinct Unicode sizes use deterministic ordering for checkout idempotency; historical hashes remain accepted on replay.

Schema `user_version` migrates sequentially **0 → 1 → 2 → 3** in an atomic transaction. The v1 size-limited variants table and COD-only orders CHECK constraint are rebuilt. Existing product IDs, variant stock, user/session data, raw order snapshots, historical idempotency hashes/keys, timestamps, seed history and order/session indexes remain. V2 adds identifier indexes, payment fields, provider ID uniqueness and processed-event storage. V3 adds `sold_out_at`, `archived_at`, the lifecycle index and the `image_uploads` registry. No reseeding/replenishment occurs for databases with the demo seed marker. Future schema versions fail closed. Back up before deployment; never replace an existing database to migrate. Use a SQLite-aware backup including committed WAL state, coordinated with a backup of the **private photo directory**. Persist both database and photos across deployments and test restoring them together; a database backup alone contains no uploaded image content. Tests use only isolated databases, not the live store.

Regular admin product arrays replace the specified product's sizes/stock atomically, as before. For a retained size, omitted optional barcode/SKU fields preserve existing identifiers; an explicit empty string clears an identifier. Duplicate barcodes return friendly **409** errors without raw SQL. Cancellation can recreate a removed size with its historical barcode/SKU. If that barcode has since been assigned elsewhere, or an existing variant's identity changed, cancellation fails **atomically with 409**, without changing order status or restoring any lines. Resolve the conflicting identifier first; do not force stock onto an unrelated variant.

### Administrator access and direct photos

The website now has a separate **`/admin/login`** sign-in page leading to **`/admin`**, while customers keep **`/account`**. Server-side `POST /api/auth/admin/login` checks both the password and administrator role; signing in never promotes a customer. It shares the normal authentication rate limiter. Invalid administrator credentials/role leave an existing customer session unchanged.

For an owner whose email already exists as a customer, the private **`admin:setup`** interactive script provides explicit promotion and password replacement, with typed email confirmation and two hidden password prompts. It preserves account IDs/orders and revokes the target account's old sessions. It can also create a new admin. It is restricted to an existing database within the website's private data directory and must not be exposed as an HTTP API. The `admin:create` alternative remains create-only. See [owner setup](../README.md#private-owner-setup-new-or-existing-email) for operational restrictions. **No owner setup was executed; no password or role change is claimed.** Updated routes require a later approved build/restart.

Admin endpoints require the server-side `admin` role; an existing signed-in customer remains restricted. The private `admin:create` CLI creates new accounts only and rejects existing emails without promotion or password changes. The current owner's role was not verified during the static review. If an authorized operator previously granted access and revoked old sessions, sign out and sign back in using that account's existing password in an approved environment. Reauthentication alone does not promote an account. If still restricted, have the authorized operator check the account role and intended website database without resetting the database or bypassing authentication. Existing-account promotion is separately authorized private administration, not a public promotion API. Never include real account identifiers or credentials in documentation/source.

In the product editor, use **Upload main photo** or **Upload gallery photos** for non-animated **JPEG/PNG/WebP**, at most **10 MiB and 40 million pixels per file**. The frontend validates the selection then sends **one file at a time**; the server verifies actual framing and decoding. Previews and main/gallery paths update only after server confirmation. A gallery holds at most **12** paths. Earlier completed uploads remain if a later file fails. **Save product** attaches paths; cancelling does not save the draft. HTTPS URLs and safe same-site paths remain editable alternatives, and a blank gallery uses the main image. Direct uploads do not require a rebuild.

`POST /api/admin/uploads/images` accepts raw binary bytes, **not multipart, JSON or base64**, with exact `Content-Type: image/jpeg`, `image/png` or `image/webp`, an admin session and `X-Requested-With: UrbanKashi`. Cross-site writes are rejected; authorization/admission precede buffering. The default limit is 30 uploads per admin per minute and two concurrent server processing slots (the frontend itself remains sequential). Success returns **201** `{path,bytes,width,height}` with a registered `/uploads/products/<uuid>.webp` path.

The server applies orientation, converts to sRGB and compresses to **WebP quality 82**, fitting within **1600 × 1600 px without upscaling**. It retains only the optimized file, not the original. Product records store image paths, and the registry stores metadata; image content lives in files rather than database blobs/base64. **Files use real disk storage**. Guarded GET/HEAD serving exposes registered WebP files, not the private directory generally.

The default is the private **data/product-images** directory beside the default database. `UPLOADS_PATH` is a server-only path override; blank is valid because the entry point passes `process.env.UPLOADS_PATH || undefined`, choosing the database-sibling `product-images` directory. Keep it outside public/static roots and persist it alongside database storage. The default managed-upload quota is **200 MiB**, including matching crash leftovers. Trusted integrations can override `AppOptions.uploadsQuotaBytes`; **no environment quota setting exists**. Full quota/disk returns 507; compression does not promise zero storage or unlimited uploads.

Unreferenced uploads older than **24 hours** are eligible for cleanup, not immediately deleted. A first unreferenced observation is followed by a second reference check **at least 60 seconds later**, under the SQLite write lock before deletion. All product main/gallery paths, including hidden and archived products, and historical order images retain their files. Replacing/removing a path only makes its former upload a candidate if no other reference remains. **Product archiving never deletes referenced photos.**

### Sold-out display, archive and republish

- When **all sizes have zero stock**, the server records `soldOutAt`. An **Active** product shows **Sold out on its image for 48 hours**, then is soft-archived and hidden from the storefront, including public detail lookup. It remains visible/editable in admin with lifecycle timestamps.
- Soft archiving preserves variants, barcodes, order snapshots and referenced images; it is not a product or photo deletion. There is no product-delete endpoint.
- Restocking positively **before 48 hours** clears the timer. Once archived, restocking alone does not publish the item: at least one size must have positive stock **and Active must be explicitly selected** when saving. API republishing requires explicit `active: true`; CSV requires explicit `active=true`. Cancellation-restored stock alone does not republish archived products.
- Background maintenance runs every **60 seconds** for archiving and image cleanup. Lifecycle checks also occur at request time and startup so persisted deadlines catch up after downtime. Legacy zero-stock rows receive a timer at their first lifecycle check. The maintenance job does not expire payment reservations or reconcile payments.

### CSV template and API

Download **`/catalogue-template.csv`**, sourced from [public/catalogue-template.csv](../public/catalogue-template.csv) and copied by the normal frontend production build. It contains two sizes of one dummy white shirt and a separate navy slug. Replace all dummy values and images before activating real inventory. **Catalogue imports accept CSV only, not XLSX workbooks**; photo uploads are separate. In Excel, set barcode and SKU columns to **Text before entering/importing codes**, then save as **CSV UTF-8**. In admin, select the CSV → Preview / जाँचें → correct errors and review warnings → explicitly approve the exact rows → Confirm import. Editing CSV invalidates the preview and approval; a connection interruption requires checking current inventory before previewing/importing again.

Required canonical headers (all must be present):

`slug,name,category,brand,design,color,size,barcode,sku,price,stock,image,description`

- One record per **size**, grouped by slug. Repeat identical product-level metadata in all rows of that slug; conflicting metadata/colours/prices, duplicate sizes or duplicate barcodes are errors.
- UTF-8 CSV supports BOM, quoted commas, escaped quotes, quoted multiline fields and Hindi text, using `csv-parse/sync` with casting disabled. In spreadsheet software explicitly format barcode and SKU columns as **text before entering/importing them**; the server cannot restore zeroes already removed by a spreadsheet. Row errors use logical CSV record numbers including the header; a quoted multiline cell counts as one record.
- **Barcode is mandatory on every imported row**, even for a legacy product. Size and absolute stock are required. Stock is 0–1,000,000; integer rupee price is 1–1,000,000.
- New products require valid slug, name, category, colour, price, image and description. Categories: Shirts, T-Shirts, Trousers, Kurtas, Layers. Defaults: active true, featured false, originalPrice null, details empty, image also used as the initial gallery image, blank brand/design allowed.
- Optional headers: `originalPrice`, `images`, `details`, `badge`, `active`, `featured`. Arrays use JSON in quoted CSV cells, booleans exactly true/false, and literal `null` can clear originalPrice. Images must be safe same-site paths or HTTPS URLs.
- Upsert is by slug (including inactive/archived products). **Only supplied sizes are updated**; absent sizes and omitted products remain. Blank metadata and blank SKU preserve existing values. Supplied nonempty values replace existing metadata; changing a nonempty barcode emits a preview warning, including the historical-cancellation implications. Another variant's barcode cannot be transferred silently, even within a batch. Archived products require positive stock and explicit `active=true` to republish; stock-only imports leave them archived.
- **Stock is absolute website-allocated sellable stock, not an increment, physical stock or live POS sync.** Reimporting resets the supplied counts. Take already-reserved orders into account before preparing the CSV; repeatedly importing an old stock file after sales can incorrectly replenish availability. This is an owner-controlled stock adjustment, not automatic inventory synchronization.

`POST /api/admin/catalogue/import/preview` accepts `{csv:string}` and returns `{valid,rows,products,variants,errors:[{row,message}],warnings:[]}`. Preview is read-only and returns validation failures in a 200 response; invalid body/auth/security uses normal HTTP errors.

`POST /api/admin/catalogue/import` accepts the same body and returns `{created,updated,variants}`; variants counts **supplied rows**, not all retained variants. Final commit replans and revalidates against the current database under a transaction. Validation failure returns 400 with `{error,errors}` and writes nothing. A later database conflict rolls back the entire batch. Preview is not a reservation or guarantee that a subsequent commit remains valid.

Both endpoints require admin authentication and the XHR header. The **entire JSON request body** is limited to 2 MiB (CSV plus JSON escaping overhead); maximum 1000 data records. All other normal JSON API bodies remain limited to 32 KiB. There is no destructive delete-by-omission or POS connection.

## Brand asset notes

The bilingual अर्बन काशी / URBAN KASHI logo uses locally served **Noto Serif Devanagari** in the website. The gold trishul is a **new crisp vector interpretation**, not a genuine recovered original or exact traced restoration. Its animation is an upright vertical-axis `rotateY` turn; text stays still and reduced-motion/print disable the turn. The downloadable [public/brand-logo.svg](../public/brand-logo.svg), served at `/brand-logo.svg`, is static. Its Unicode text is **font-dependent and not outlined**; no fonts are embedded or remotely fetched. Use an appropriate locally installed Devanagari font, or produce a separately outlined version in a vector editor for identical standalone print rendering.
